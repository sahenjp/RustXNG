# 自前インデックス（ローカル BM25）

> **実験機能です。既定では無効です。** `local_index_path` を設定したときだけ動きます。
> クロールとインデックスの管理が必要になるため、通常の利用では不要です。

RustXNG は上流エンジンに依存しない**自前の全文検索インデックス**を持てます。ローカルのヒットを上流の結果に足すことで、上流が取りこぼすページを補い**精度が上がります**。

## 構成

```text
rustxng-index crawl   →  Tantivy インデックス（BM25）
                            ↓
rustxng（--port 8888）  →  ローカルのヒットを上流の結果に併合
                            ↓
                        175 の上流エンジン
```

- **転置インデックス**: Tantivy（Rust 製、BM25 でスコアリング）
- **二重トークナイズ**: 空白区切り言語は既定トークナイザ、日本語・中国語は**文字バイグラム**（分かち書きが無いため）
- **礼儀**: robots.txt の `Disallow` を尊重、同一ホストのみ辿る、ホストごとに間隔を空ける、200 ページごとにコミット
- **読み書き分離**: クロール中でも検索側は読み取り専用で開ける

## 使い方

```bash
# 1. シードを用意（1 行 1 URL）
https://doc.rust-lang.org/book/
https://docs.python.org/3/library/

# 2. クロール（robots.txt を尊重、8 ワーカー）
rustxng-index crawl --seeds seeds.txt --out ./index-data --max-pages 5000 --max-depth 3 --workers 8

# 3. 確認
rustxng-index stats --index ./index-data
rustxng-index search --index ./index-data "python dict get" --limit 5

# 4. サーバー起動（index-data/ があれば自動で併用される）
rustxng
```

## 設定

```toml
[search]
local_index_path = "index-data"   # 既定は空（無効）。設定すると有効になる
local_index_merge = true          # false にするとインデックスを保持したまま順位から外す
```

**既定では無効です。** 上の local_index_path を設定したときだけ併用が始まります。

## 実測（100 問）

| 構成 | hit@1 | hit@5 | MRR | レイテンシ |
| --- | ---: | ---: | ---: | ---: |
| インデックスなし | 79 | 92 | 0.853 | 933〜1,035 ms |
| **ローカル併用（5,000 ページ）** | **83** | **96** | **0.889** | 832〜1,469 ms |
| Exa | 77 | 91 | 0.840 | 598 ms |

2 回計測して同じ値（83/96/0.889）でした。上流が既に取れているページを重ねても伸びないため、**5,000 ページで頭打ち**になります（7,600 ページでも同値）。

## クロールの性能

| ページ数 | 所要時間 |
| ---: | ---: |
| 5,000 | 12.5 分 |

8 ワーカー、ホストごと 150 ms 間隔。並列化前は同規模で 1 時間以上かかっていました。

## 制約

- **即答モードはありません**。ローカルだけで答えるとインデックスに無いページを拾えず精度が落ちるため（実測 72/82）、上流との併合だけを残しました
- クロールは単一プロセス内の並列で、差分更新と sitemap 対応は未実装です
- Wikipedia は全文クロールが非現実的なため、記事 URL を直接シードしています

### インデックスを育てても精度は伸びない（実測）

| インデックス | hit@1 | hit@5 | MRR |
| --- | ---: | ---: | ---: |
| なし | 79 | 92 | 0.853 |
| 5,000 ページ（リンク辿り） | **83** | **96** | **0.889** |
| 7,200 ページ（sitemap） | 81 | 93 | 0.871 |
| 15,000 ページ（広いシード） | 80 | 93 | 0.863 |

**5,000 ページで頭打ち**です。ページを増やしても、上流エンジンが既に取れているページを重ねるだけなので精度は上がりません。差が出るのは「上流が落としているページ」を拾えたときだけで、その機会はインデックスを広げても増えませんでした。

つまり自前インデックスの価値は**精度ではなく速度**（将来の即答）にあり、それにはクエリの答えをほぼ網羅する規模が必要です。

### 127,200 ページまで育てた結果

120,000 ページを追加クロールして 127,200 ページ（1.1 GB）にした時点で測り直しました。

| インデックス | hit@1 | hit@5 | MRR |
| --- | ---: | ---: | ---: |
| なし | 79 | 92 | 0.853 |
| 5,000 ページ | **83** | **96** | **0.889** |
| 15,000 ページ | 80 | 93 | 0.863 |
| **127,200 ページ** | 82 | 94 | 0.876 |

**規模を25倍にしても 82/94/0.876 で、5,000 ページと変わりません。** 精度はインデックス規模ではなく「上流が落としているページを拾えたか」で決まるため、5,000 ページで実用上の上限に達しています。

一方でコストは増えます（1.1 GB、クロール約2時間）。**精度目的でインデックスを育てるのは無駄**という結論です。
