# 構成ごとの比較（2026-11-04）：通常版・フル版・クリーン版・Exa・Tavily

**履歴資料です。** これは2026年11月4日の旧プロファイル（v0.28.0開発時点）を使った観測であり、**v0.30.0のStandard・ローカル索引専用Clean・現在のFullの性能ではありません**。検索元・既定設定・許可条件は変更されています。現在の構成は[README](../README.ja.md)と[監査記録](PROVIDERS.md)、11月5日の[Standard測定](ISSUE-RESOLUTION-2026-11-05.md)、[現在のCleanの保存測定](CLEAN-PROFILE.md)を参照してください。

同じ質問集・同じ採点で、当時のRustXNGの3構成とExa・Tavilyを並べました。

構成は起動時に `--profile` で切り替えます（環境変数 `RUSTXNG_PROFILE` でも可）。

| 構成 | 起動 | 中身 |
| --- | --- | --- |
| フル版 | `rustxng --profile full`（`settings.full.toml`） | 通常版＋禁止・制限・許諾未確認の検索先（Yahoo、Yahoo! JAPAN、NAVER、Keenable、fynd）。**個人利用でも規約は適用され、適切な許諾なしに禁止された取得方式は利用できない**（[プロバイダー監査](PROVIDERS.md)） |
| 通常版（既定） | `rustxng`（`settings.toml`） | キー不要でアクセス拒否の少ない検索先が中心。ただし **Bing・Seznamなど許諾未確認の経路を含む** |
| クリーン版 | `rustxng --profile clean`（`settings.clean.toml`） | 公開APIの許可リストと自前クロール索引。**各APIの利用条件・再配布の許諾を一律に保証するものではない** |

**Exa と Tavily は API キーがないため今回は問い合わせていません。** リポジトリに保存済みの全問結果（`bench/content-exa.json`・`bench/content-tavily.json`、技術文書 100 問）を、同じ採点器で採点し直した値です。取得日が違うため、厳密な同時比較ではありません。

全問の結果は `bench/results/profiles-2026-11-04/`（構成ごとに `docs100.json` と SealQA の観測）にあります。

**測定時のソース来歴にも注意してください。** SealQAの保存メタデータはコミット`9e77a137`を記録していますが、v0.28.0のリリースは`0f2ddea9`で、間に検索機能を含む7コミットがあります。測定時の未コミット変更やバイナリの同一性もこの記録だけでは検証できません。この表は**2026-11-04の開発途中に保存した観測値**であり、v0.28.0配布バイナリそのものを再測定した値とは断定しません。

## 読み方

- **フル版は、技術文書でも SealQA でも最も強い構成です。** 技術文書は Exa を上回り（MRR 0.878 対 0.840）、SealQA は変更前の通常構成（hit@10 156）を上回りました。差を作っているのは Yahoo! JAPAN（SealQA で正解を含んだ回数 121）と Keenable です。
- **通常版は、技術文書で Exa の保存結果に近い値でした**（hit@5 87 対 91）。Tavily の保存結果より高い値ですが、同時刻・同条件のライブ比較ではありません。応答は 3 構成で最も速い（中央値 0.66 s）。Bing・Seznamなどの利用条件は未確認のままです。
- **クリーン版**（公開 API と自前の索引だけ）は、今日 28 → 61（hit@10）まで上げましたが、Exa には届きません。残りの差は、外部の Web 検索がないと見つけにくいページです（GitHub のリポジトリ、`docs.kernel.org` のような別ホストの文書、索引にない公式サイト）。

## 今日入れた改善

| 改善 | 内容 | 効く構成 |
| --- | --- | --- |
| 日本語の質問は日本語版 Wikipedia へ | UI の言語（既定 `en`）が検索言語に流用され、日本語の質問が英語版に送られていた。言語の指定がなければ質問の文字種で決める | 全部 |
| 公式サイト・リポジトリ・論文を Wikidata から | 見つかった Wikipedia 記事の公式サイト（P856）、質問に「github」「arxiv」があればリポジトリ（P1324）・arXiv（P818）を 1 回の SPARQL で引く（`src/official.rs`） | 全部 |
| サイト名で専門エンジンを呼ぶ | 「… arxiv」「… npm」のように名指しされたら、そのエンジンにサイト名を除いて渡し、重みを 2 倍にする | 全部 |
| ページの言語 | URL に言語が書かれたページ（`/ja/`、`/ja-jp/`、`ja.react.dev`）を、質問の言語と合えば少し上げ（質問との一致度に比例）、第三の言語なら下げる | 全部 |
| arXiv の検索を題名で | 文を `all:` に渡していたのを、題名の句または全語一致に。URL も版番号なしに | 全部 |
| Wikipedia の重複投票をやめる・URL を正規の表記に | 補助エンジンが同じ記事に 3 票入れていた。`%28` 形式の URL が他の結果と統合されなかった | 全部 |
| 雑音の多いエンジンを一般検索から外す | Wikibooks など姉妹プロジェクト 6 件（bang では使える）と Grokipedia。どちらの質問集でも正解を 1 件も返さなかった | 通常・フル |
| 待ち時間を減らす | 自前索引の検索をエンジンと並行に。Wikidata の問い合わせを Wikipedia の応答直後に始め、エンジンが終わった後は既定 400 ms までしか待たない | 全部 |
| ホストごとの間隔を個別に | `[outgoing.host_spacing_overrides]`。クリーン版は全ホスト 1.1 秒間隔のまま、Wikipedia だけ 200 ms（Wikimedia は読み取りに固定の上限を設けていない） | クリーン |
| 自前クローラー | サイトマップの上限をホストごとに、`--within-seed-path`、`--skip-indexed`。DevDocs の一覧・主要文書サイト・公式文書の日本語版（`bench/clean-profile/seeds-ja.txt`）から 41,144 ページ・125 MB | 通常・クリーン |
| 名前だけで既定のエンジンを上書き | 構成ファイルの `[[engines]]` に `name` と `disabled` だけ書けばよい（新しいエンジンは従来どおり `engine` が必要） | — |

## 注意

- **自前索引のシードと、この 100 問の正解のサイトは重なっています**（docs.python.org、MDN、React の日本語版など）。シードは正解の URL から作ったものではなく、一般的な文書サイト・DevDocs の一覧・公式文書の日本語版から取りました。それでも、この 100 問では自前索引が有利に出ます。
- 改善の多くは、この 2 つの質問集の外れ方を見て見つけたものです。手法はどれも一般的ですが、別の質問集での確認が望ましいです。
- 各構成ほぼ 1 回ずつの測定です。上流の検索結果は日によって変わり、同じ設定でも数問ぶん揺れます。
- フル版の Yahoo（米国）は、5 回に 1 回ほど接続を切られ、再試行で遅くなります。Keenable もときどき同じ結果を繰り返し、その応答は捨てています。
- 上の数字は、索引（`index-docs`、`index-wikipedia`）を作った環境のものです。索引がない環境では、通常版の技術文書は hit@10 87 前後（自前索引なしで測定）になります。
- **SealQAの保存済み`metadata.json`は、評価スクリプトの固定文言で`no local index`と記録していますが、索引の有効状態を調査していません。** この記述を索引が存在しなかった証拠として使わないでください。実効設定と索引の生成物を含む来歴が必要です。
- 未見の設問での再測定と、公開APIの再配布・利用条件の確認は別途必要です。
